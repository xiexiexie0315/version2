# 自瞄三阶段实施方案

## 当前范围

当前只实施第一阶段：保留已经实车验证可用的导航与下位机串口链路，选择一版
自瞄接入这条链路，只控制云台，不控制开火。导航源码和下位机源码不在本次
改动范围内。

选用原 `standard_mpc` 的检测、跟踪和 MPC 解算流程，新增入口
`standard_mpc_ros2`。算法仍是普通 C++；只有输入输出适配层使用 `rclcpp`，
所以“导航是 ROS2、自瞄是 C++”并不冲突。ROS2 本身就提供 C++ API。

## 第一阶段：基础自瞄

运行时只复用导航包中的两个硬件节点：

```text
下位机
  <-> 已验证可用的 USB 串口协议
standard_robot_pp_ros2
  -> serial/imu
  -> serial/gimbal_joint_state
  <- cmd_gimbal_joint
gimbal_manager
  <- cmd_gimbal
standard_mpc_ros2
```

第一阶段不要启动导航的装甲板识别、弹道、射击或其它云台命令发布者，也不要
让导航相机驱动与自瞄同时打开同一台工业相机。这样串口仍只有一个拥有者，
相机和云台命令也都只有一个拥有者。

### 第一阶段最低数据

下位机到上位机必须持续提供：

- IMU 姿态：四元数，或可无歧义转换成四元数的 yaw/pitch/roll；
- 三轴角速度，单位和正方向固定；
- 采样时间或稳定的接收周期，供相机帧与姿态对齐；
- 实际云台 yaw/pitch 反馈；
- 云台已归中、允许自动控制的状态，至少能由遥控器和电控状态机可靠保证。

当前导航已经把前四项中的姿态、角速度和云台角发布为 `serial/imu`、
`serial/gimbal_joint_state`，因此基础转向不要求先修改下位机协议。

### 建议电控现在补齐的数据

下面这些不阻塞“先让云台转起来”，但会影响后续精度和安全，建议现在预留：

1. 实测弹速，单位 `m/s`，建议 10--20 Hz，并附更新时间；可复用现有
   `ID_DEBUG`，名称固定为 10 字节 `bullet_spd`，导航会发布
   `serial/debug/bullet_spd`。在它接通前，自瞄使用配置项
   `ros2_gimbal_bullet_speed`，当前为 `22.0`。
2. 云台模式、归中完成、上位机控制使能和故障状态；不能只靠上位机猜状态。
3. 编码器闭环的实际 yaw/pitch，而不是仅有 IMU 欧拉角。
4. 通信心跳或有效帧时间；失联后 200--500 ms 内退回安全状态。
5. 协议版本号和单位标志，避免以后 rad/degree 或帧版本混用。

本阶段不需要弹丸计数、开火、摩擦轮、裁判血量或导航定位数据。射击相关源码
保留，但 `standard_mpc_ros2` 固定忽略 `fire`，且不发布 `cmd_shoot`。

### 不要改动已验证链路

已实车验证的导航/下位机收发方式作为基线，不因为源码目录中的试验性改动而
直接重写 CRC、字节转义或帧结构。只需让电控确认“实际烧录固件”与提供给我们
检查的源码版本一致。若以后增加字段，优先增加新帧 ID 或协议版本，不要改变
现有可用帧的长度和含义。

角度单位由自瞄配置显式适配：如果现有链路的云台命令最终按 degree 使用，
`ros2_gimbal_yaw_scale`、`ros2_gimbal_pitch_scale` 保持 `57.2957795`；如果实车
链路已经按 rad 使用，两项改为 `1.0`。只能选一种，首次必须用 `0.05--0.1 rad`
单轴小角度验证。

## 第二阶段：全向感知

第二阶段在第一阶段入口上增加同济方案的多相机/全向检测与目标融合。通信层、
云台控制接口和开火禁用策略继续复用，不在当前阶段实施。

## 第三阶段：导航和自瞄同时运行

无论选哪种进程间通信，必须满足一个原则：USB 串口只能有一个进程拥有，云台
最终命令也必须经过一个仲裁器。

### 方案 A：ROS2 话题，推荐

保留 `standard_robot_pp_ros2` 为唯一串口拥有者。导航和自瞄都作为数据消费者，
分别发布带来源的话题，例如 `cmd_gimbal_nav`、`cmd_gimbal_aim`，再由独立仲裁器
根据遥控器模式、目标状态和超时生成唯一的 `cmd_gimbal`。

优点是改动最小、类型和时间戳明确、现有导航工具可直接观察和录包。自瞄核心仍
是 C++，只在边界使用 ROS2 C++ API，不需要改写算法。

### 方案 B：C++ 网关加本机 IPC

若不希望自瞄核心依赖 ROS2，可让一个独立 C++ 通信网关独占串口，自瞄通过
Unix domain socket、UDP loopback 或 ZeroMQ 与网关通信；导航侧增加一个很薄的
ROS2 适配节点，把 IPC 数据转换成现有话题。

这比方案 A 多一套消息定义、序列化、心跳和重连机制。优先顺序建议为 Unix
domain socket、ZeroMQ、UDP；不建议用共享文件。即使采用该方案，也应把网关
独立于检测/推理进程，避免自瞄崩溃时连带切断导航通信。

### 方案 C：自瞄进程作为串口中间人

技术上可行，即“下位机 -> 自瞄 -> 导航”，但不建议作为最终架构。自瞄推理、
相机或模型一旦异常，导航会同时失去下位机数据；重启自瞄也会重置整车串口。
如果必须采用，至少把串口转发放在自瞄工程内的独立进程，不要放进推理主循环。

第三阶段推荐的数据流是：

```text
下位机 <-> 唯一通信网关
                 -> 导航
                 -> 自瞄
导航命令 -----> 云台/底盘仲裁器 -----> 通信网关
自瞄命令 -----> 云台/底盘仲裁器 -----> 通信网关
```

第一阶段交付已经采用方案 A 的输入输出边界，后续增加仲裁器即可扩展到同时运行，
不需要推翻自瞄检测和 MPC 解算代码。
